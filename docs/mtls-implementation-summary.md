# mTLS Implementation Summary

## Result

mTLS between Kong and the FastAPI upstream services was implemented and tested successfully.

The current network plane is now:

```text
Client
  -> HTTPS / Kong
  -> mTLS / FastAPI upstream services
```

Kong still verifies each upstream service certificate, and each FastAPI service now requires a client certificate from Kong.

## What changed

### Certificate generation

Updated `scripts/generate-dev-certs.sh`:

- Generates the internal CA as before.
- Generates Kong external TLS certificate as before.
- Generates a new Kong upstream client certificate:
  - `gateway/certs/kong-upstream-client.crt`
  - `gateway/certs/kong-upstream-client.key`
- Copies the same client certificate/key into each service cert folder as `health-client.crt` and `health-client.key` so Docker healthchecks can call the mTLS-protected health endpoint.

### Kong declarative config

Updated `gateway/kong.template.yml`:

- Adds a `certificates` entity for Kong's upstream client certificate.
- Adds `client_certificate` to every upstream service:
  - `user-service`
  - `resource-service`
  - `admin-service`
  - `payment-service`

Updated `scripts/kong-init.sh`:

- Ensures Kong upstream client cert/key exist.
- Renders the client cert/key into `gateway/kong.yml`.

### FastAPI services

Updated `docker-compose.yml` for all four services:

- Uvicorn now runs with:

```text
--ssl-ca-certs /certs/ca.crt
--ssl-cert-reqs 2
```

`--ssl-cert-reqs 2` means client certificates are required during TLS handshake.

Healthchecks now use a trusted client certificate:

```text
/certs/health-client.crt
/certs/health-client.key
```

Without a client certificate, direct TLS requests to the service are rejected.

### Tests

Updated `scripts/test-tls-plane.sh`:

- Verifies Kong external TLS certificate.
- Verifies upstream service certificate trust.
- Verifies service rejects a request without client certificate.
- Verifies service accepts Kong upstream client certificate.
- Verifies Kong can still route to the HTTPS upstream.

Added/updated gateway config tests:

- `tests/test_gateway_config.py`


## Current limitation

This is real mTLS for Kong to upstream services in the lab deployment. It is still lab certificate management:

- Certificates are generated by `scripts/generate-dev-certs.sh`.
- Certificates are self-signed by the lab internal CA.
- Production should issue and rotate these certificates through Vault PKI or another managed CA.
- The same Kong upstream client certificate is used for all upstream services. Production can split this into per-service client certs if stricter identity is required.

## Demo wording

Recommended wording for the final demo:

```text
External clients access the API through HTTPS at Kong/Caddy. Internally, Kong calls each FastAPI service over mTLS. Kong verifies the service certificate, and each service requires a client certificate signed by the internal CA. A direct request without a client certificate is rejected, while Kong's upstream client certificate is accepted.
```

Do not claim production-grade certificate lifecycle yet. Claim mTLS enforcement and show the test output above.
